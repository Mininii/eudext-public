# eudext 비용 측정 기록

`tools/cost.py` 가 덧붙인다(DESIGN 3.8, 5.2). 단위는 트리거 수(본문·호출 자리·실행)와 바이트(페이로드).

- 본문: EUDFunc 한 벌의 트리거 수(`f.size()`). 인라인 부품이면 `-`.
- 호출 자리: 그 코드가 호출한 자리에 낸 RawTrigger 수(`GetTriggerCounter()` 차이, 본문 제외).
- 실행: 에뮬레이터 한 사이클에서 그 코드가 실행한 트리거 수(변수 트리거 포함). 입력에 따라 다르면 최소~최대.
- 페이로드: 그 코드를 40벌 넣은 빌드와 빈 빌드의 페이로드 차이 ÷ 40 (적층 뒤, 셔플 끔, 변수 트리거 72B 포함).
  적층 배치가 전체에 따라 달라져 한 벌만 넣고 재면 ±1KB 흔들리므로 나눠서 적는다. **참고값**이다.

측정: `EUDEXT_WORK=… .venv/bin/python eudext/tools/cost.py eudext/tests/t_cmp.py --title "cmp (WP1)" --append --out <파일> --bytes`
(항목 정의는 `tests/t_cmp.py` 의 `COST_CASES`, 용어 "칸" = EUDLightVariable 같은 읽기 전용 값 칸).

읽는 법 (cmp 표만의 약속):
- **조건을 돌려주는 줄에는 그 조건을 담는 소비 트리거 1개**(`Trigger(conditions=…)`)가 호출·실행 수에 들어 있다
  (첫 줄 "소비 트리거만" = 1 / 1). cmp 자체 비용 = 표 값 − 1.
  예: `ge(변수, 상수)` 1 / 1 → cmp 는 트리거 0, `ge(변수, 변수)` 2 / 3 → cmp 는 호출 1 / 실행 2.
  `f_wread_signed`·`f_bread_signed` 줄은 값을 돌려주므로 소비 트리거가 없다.
- 목표(DESIGN 4.2 "상수 0~2, 변수끼리 호출 2~3")를 표의 `call≤` 에는 소비 트리거를 더해 적었다(상수 1·3, 변수 4).
- cmp 자체 비용 요약:
  - 상수 비교 0 / 0.
  - OR 이 되는 상수 비교(`ne(x, 5)`, `sge(x, -5)`, 0 을 걸친 부호 구간): 변수 1 / 2, 칸 2 / 2.
  - 변수끼리 `ge`·`le`·`gt`·`lt`·`eq` 1 / 2, `ne`·`sge`·`sle`·`sgt`·`slt` 1 / 3. 칸과 변수도 `ge` 류 1 / 2, `ne` 2 / 3.
  - 변수 구간 `between(x, lo, hi)` 1 / 3 (부호 있음 1 / 4).
  - `f_wread_signed`·`f_bread_signed` = eudplib `f_wread_epd`·`f_bread_epd` + 호출 1 / 실행 1.
- eudplib 0.81 연산자와 비교 (둘 다 소비 트리거 포함):
  - `a < b` 2 / 4 · 888B → `cmp.lt(a, b)` 2 / 3 · 640B
  - `a != b` 3 / 5 · 1016B → `cmp.ne(a, b)` 2 / 4 · 871B
  - `a != 5` 2 / 3 · 632B → `cmp.ne(a, 5)` 2 / 3 · 560B
  - `a >= b`·`a == b` 는 cmp 와 같다(2 / 3 · 582B). eudplib 은 조건을 소비할 때, cmp 는 부를 때 채운다.

목표를 넘은 줄:
- `sge(칸, 변수)` 호출 5(cmp 자체 4) / 실행 6: 한쪽이 EUDLightVariable 같은 읽기 전용 칸이면 부호 비트를 뒤집은 값을
  조건 칸에 채울 수 없어서, 부호 없는 비교 1 + 부호 보정 트리거 2 + 깃발 준비로 푼다. 칸의 값을 제자리에서 잠깐 뒤집었다가
  되돌리면 3 / 4 까지 줄일 수 있지만 호출한 쪽의 메모리를 건드리는 방법이라 쓰지 않았다. 부호 있는 "칸·변수" 비교는 드문 조합이다.
- `ge(칸, 칸)` 호출 4(cmp 3) / 실행 40: 두 쪽 다 채울 수 없는 칸이면 한쪽을 `f_dwread_epd` 로 읽는다(목표 표에 없음, 참고).

**3.8 목표와 비교**
- "유닛별 저장 1700×N 은 EUDArray, scx 증가 < 1KB": 1700×6 이 +442B 로 **충족**(필드 20개면 +1.2KB — 필드 수에 거의 비례, 필드당 약 40~60B). 저장은 필드마다 1701칸 dword(마지막은 빈 칸 없음용 버리는 칸)를 한 `Db` 에 이어 둔 것으로, EUDArray 와 같은 칸당 4B 다.

- 죽은 유닛 순회: clear_on_death 1,957 / dying 1,874 실행/사이클(chunk 20). 원본 EXCC 는 유닛 트리거 1700개 + 걸린 유닛마다 복사 사슬이었다. chunk 50 이면 1,874 로 조금 줄고 호출 자리는 25 → 59 로 는다.

- **나머지(`%`)와 32의 배수 시프트는 완승**이다 — `x % 16` 3 실행 / 991B, `x // 2^64` 3 실행 / 1121B. 기존 길은 둘 다
  40~215 실행에 제수마다 약 47KB 본문이었다.
- **몫은 맞바꾸기**다. 32 로 안 나누어떨어지는 시프트(제수 2·4·16…)는 굽는 본문이 139트리거(i128 9 + i64 상수 130,
  약 47KB) → 63트리거(i64 상수 시프트, 약 20KB)로 **제수마다 약 −27KB** 지만, 사본마다 +1.4KB 고 값이 2^64 미만일 때
  실행이 40 → 73 으로 는다(2^64 이상은 212 → 211 로 같다). 사본이 약 18곳을 넘으면 용량도 손해다.
  값이 64비트 안이면 창 하나로 끝내는 빠른 길을 `_cdiv_fn` 과 같은 모양으로 넣어 놓아서 그나마 73 이다.
  느려지는 쪽은 i64 의 작은 n 오른쪽 상수 시프트 본문(`_shr_k_emit` 비트 옮기기 61트리거)이 원인이다 — 그쪽을 빠르게
  하면 이 길도 같이 빨라진다(후속 후보).
- **`CONST_DIVISOR`**(i64·i128 각각): 상수 제수 전용 본문을 굽지 않고 변수 제수 공유 본문으로 보내는 용량 스위치.
  기본 True(빠른 쪽). 끄면 상수 종류마다 i64 약 36KB / i128 약 47KB 가 통째로 사라지는 대신 실행이 3~4배가 된다
  (i128 40~215 → 72~680, i64 12~79 → 26~314). 2의 거듭제곱 접기는 이 스위치와 무관하게 늘 한다(더 싸다).
  **성능 우선 원칙(3.8)에 따라 기본값은 건드리지 않는다** — 용량이 정말 급한 맵이 켜고 끄며 `tools/size_report.py`
  로 견주라고 둔 것이다.

## tools/size_report.py — 페이로드를 만든 자리별로 (2026-09-20)
